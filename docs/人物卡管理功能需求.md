# RPBox 人物卡管理与个人展示墙需求

> 状态：MVP 已实现；安全发布与多版本写回迭代开发中（2026-08-11）
> 关联任务：`SYNC-0015`、`SYNC-0017`、`COMM-0001`
> 界面参考：[`docs/design/rpbox-character-cards-gent-reference.png`](./design/rpbox-character-cards-gent-reference.png)
> GentWorkflow 任务：`7d3f8c7b-806c-58b4-b14e-ec2b49289187`

## 1. 产品意图

在个人中心增加“人物卡展示墙”，把人物设定从单纯的 TRP3 备份数据升级为可创作、可展示、可在社区内容中传播的 RPBox 原生资产。

本功能必须同时满足三件事：

1. 没有任何人物卡时，用户能明确地从零创建，或从已有云备份的人物卡开始。
2. RPBox 人物卡可以拥有完全自定义的角色大图、名称、称号和分栏剧情资料，并在个人信息页形成类似徽章墙的展示效果。
3. RPBox 人物卡与 TRP3 人物资料只在基础身份信息上显式互通；二者可以有关联，但不是强制一一对应关系。

## 2. 概念与数据边界

### 2.1 两类对象

- `Character`：现有的 TRP3/剧情归档人物对象，继续服务于游戏资料和剧情说话人关联。
- `CharacterCard`：新增的 RPBox 原生人物卡，服务于个人展示、富文本创作和社区内嵌。

`CharacterCard` 可以不关联任何 `Character`；一个 `Character` 也不限制只能对应一张 RPBox 人物卡。导入和同步是用户主动触发的复制/更新操作，不建立会自动覆盖内容的隐式同步。

### 2.2 可双向承接的基础字段

| RPBox 字段 | TRP3 字段 | 说明 |
|---|---|---|
| 名、姓 | `FN`、`LN` | 展示名可由名姓组合，但 RPBox 保留独立展示规则 |
| 称号、完整头衔 | `TI`、`FT` | 基础身份信息 |
| 种族、职业 | `RA`、`CL` | 基础身份信息 |
| 眼睛颜色、颜色值 | `EC`、`EH` | 颜色值存在时一并承接 |
| 年龄、身高、体重 | `AG`、`HE`、`WE` | 文本字段，不擅自换算 |
| 出生地、居所 | `BP`、`RE` | 基础身份信息 |
| 关系状态 | `RS` | 保留 TRP3 原值 |
| 图标、职业/名字颜色 | `IC`、`CH` | `CH` 同时驱动人物名和职业展示颜色，不代替 RPBox 角色大图 |

基础字段从 TRP3 导入 RPBox 时，以 `AccountBackup.ProfilesData` 中对应 profile 的 `player.characteristics` 为来源。同步必须针对用户本人拥有的备份，并记录来源账号、备份和 profile 标识。

桌面端将 RPBox 基础字段写回 TRP3 时，复用现有 Tauri `update_profile` 命令，只修改上表中的基础字段；操作前显示确认弹窗，成功后提醒用户重新上传备份。服务端不得仅修改 `profiles_data` 后宣称已写回 TRP3，因为恢复流程可能优先使用 `raw_trp3_lua`。

### 2.3 仅属于 RPBox 的字段

- 完全自定义上传的角色竖幅大图
- 人物卡摘要、展示铭文及展示排序
- 背景故事富文本
- 第一印象富文本
- 其他资料富文本
- 草稿/发布状态和私密/公开可见性
- 展示墙视觉表现与帖子内嵌预览

这些字段永不写入 TRP3，也不会因为重新从备份读取基础信息而被覆盖。

## 3. 核心用户流程

### 3.1 个人中心展示墙

- 入口位于个人中心，标题为“人物卡展示墙”。
- 本人查看时始终可见；访客只看到已发布且公开的人物卡，完全没有公开人物卡时不展示管理型空状态。
- 本人无卡片时显示完整空状态、用途说明和主按钮“新建人物卡”。
- 已有卡片时以高竖幅肖像卡排列；卡面显示角色大图、名称、称号和简短摘要，并提供新建入口。
- 本人的草稿或私密卡片要有清楚但克制的状态标识。
- 卡片支持点击和键盘聚焦进入详情；悬浮/聚焦时轻微抬升、铜色轮廓与信息浮层同时出现。

### 3.2 新建来源选择

点击“新建人物卡”进入来源选择：

1. **从已备份的人物卡开始**：列出当前用户云备份中的账号与 profile 摘要；选定后服务端读取对应 Lua 解析结果并复制可共用的基础字段，新建一张 RPBox 人物卡草稿。
2. **从零新建 RPBox 人物卡**：创建不依赖 TRP3 的空白草稿。

导入不会修改备份原数据。来源不存在、备份不属于当前用户、profile 已失效或 JSON 无法解析时，需要返回明确错误，不能创建半成品记录。

### 3.3 制作与编辑页面

编辑页由角色大图/身份预览区和内容编辑区组成，至少包含以下 Tab：

- **基础信息**：名称、称号、种族、职业、眼睛颜色、年龄、身高、体重、出生地、居所、关系状态等可互通字段，以及 RPBox 摘要和公开状态。
- **背景故事**：RPBox 富文本。
- **第一印象**：RPBox 富文本。
- **其他**：RPBox 富文本。

富文本区域沿用现有 `TiptapEditor` 的能力和数据格式，支持已有的内部链接、图片与 GIF。Tab 切换不得丢失未提交的编辑内容；保存时应整体一致地提交，避免出现只保存当前 Tab 的误导。

角色大图应支持多张上传、有序陈列、封面切换、预览和删除，并遵守项目图片缓存约定：列表 DTO 不返回 base64；图片使用独立图片 URL，变更时更新对应图片时间；旧 `portrait_image_url` 与 `portrait_image_updated_at` 继续作为封面兼容字段；带 `v` 的 URL 使用长缓存和 ETag。

所有颜色值编辑控件必须同时提供可视取色器和精确 HEX 输入。TRP3 `CH` 在产品文案中称为“职业/人物名颜色”，人物名在编辑预览、详情、展示墙和帖子悬浮预览中使用该颜色。

### 3.4 详情与公开访问

- 新增人物卡详情路由，公开卡片可由其他登录用户访问；私密、草稿或不存在的卡片统一按无权限/不存在处理，避免泄漏元数据。
- “已发布 + 公开可见”只是提交审核意图，不等于立即公开。首次提交在版主审核通过前只有所有者和版主可见；所有者必须看到明确的“审核中”状态与驳回原因。
- 已经审核通过的公开人物卡再次编辑时，游客继续看到最后一次通过的快照；未审核工作副本及其图片不得泄漏。
- 详情页沿用编辑页的内容分栏，但以只读方式展示。
- 本人可从详情进入编辑、切换公开状态或删除；删除必须使用 `RDialog` 确认，结果用 `RToast` 反馈。

### 3.5 帖子内部链接与 Hover

- 帖子编辑器的内部链接选择器增加“人物卡”类型，至少可选择当前用户自己的已发布人物卡；若现有选择器已支持公开资源检索，可同时展示其他用户的公开人物卡。
- 链接节点使用稳定标识：`data-jump-type="character_card"`、人物卡 ID 和目标 `/character-cards/:id`，不能把名称当唯一键。
- 编辑态、预览态和帖子详情态必须一致解析人物卡链接。
- 鼠标悬浮或键盘聚焦时显示独特的肖像预览卡，包含大图、名称、称号和摘要；交互风格与现有 `RPDBJumpPreview` 一致但具有角色肖像墙自己的铜色铭牌美感。
- 私密、删除或失效卡片要降级为不泄漏内容的“人物卡暂不可用”，不能导致帖子渲染失败。

## 4. 建议的数据模型

新增独立 `CharacterCard`，建议至少包含：

- 所有权：`id`、`user_id`
- 可选关系：`character_id`、`source_backup_id`、`source_account_id`、`source_profile_id`
- 基础字段：`first_name`、`last_name`、`display_name`、`title`、`full_title`、`race`、`class`、`eye_color`、`eye_color_hex`、`age`、`height`、`weight`、`birthplace`、`residence`、`relationship_status`、`icon`、`name_color`
- RPBox 字段：`summary`、`background_story`、`first_impression`、`other_content`
- 图片字段：角色大图存储引用及 `portrait_image_updated_at`
- 状态字段：`status`（`draft`/`published`）、`visibility`（`private`/`public`）、可选 `sort_order`
- 审计字段：`created_at`、`updated_at`

字段长度、富文本体积、图片 MIME/尺寸和状态枚举必须在服务端校验，不能只依赖前端。

## 5. API 契约

所有写接口及“我的”列表要求 JWT；所有权检查必须由服务端执行。

| 方法与路径 | 用途 |
|---|---|
| `GET /api/v1/character-card-sources` | 返回当前用户可导入的备份人物摘要，不返回原始 Lua |
| `GET /api/v1/character-cards` | 返回当前用户全部人物卡，包含草稿/私密状态 |
| `POST /api/v1/character-cards` | 以 `blank` 或 `backup` 来源创建草稿 |
| `GET /api/v1/character-cards/:id` | 返回本人卡片或已发布公开卡片 |
| `PUT /api/v1/character-cards/:id` | 更新本人卡片的基础字段、RPBox 内容和状态 |
| `DELETE /api/v1/character-cards/:id` | 删除本人卡片 |
| `POST /api/v1/character-cards/:id/sync-from-trp3` | 从记录的备份来源重新拉取基础字段 |
| `GET /api/v1/users/:id/character-cards` | 返回指定用户已发布且公开的展示墙内容 |
| `POST /api/v1/upload/character-card-portrait` | 将本人角色大图上传到受保护的 pending 存储并返回内部引用 |
| `GET /api/v1/images/character-card-portrait/:id` | 返回可访问卡片的角色大图并执行缓存/权限策略 |

接口继续遵循仓库现有请求封装；错误信息需要能区分参数错误、来源不存在、无权访问和服务端失败。

## 6. 视觉与交互方向

界面气质为“安静公会档案馆中的冒险者肖像墙”。使用项目现有暖白、深棕和铜色体系，重点色参考：

- `#EED9C4`、`#FDFBF9`、`#E8DCCF`
- `#4B3621`、`#804030`、`#B87333`
- `#2C1810`、`#8C7B70`

标志元素是高竖幅肖像、铜色徽记轨道和铭牌式姓名区。参考图用于布局、层级和氛围，不照搬其中的 AI 伪文字。界面继续使用项目已有图标字体，不新增 emoji 充当产品图标。

动效必须遵守 `prefers-reduced-motion`。Hover 信息也必须能通过 `:focus-visible` 和键盘访问获得；仅装饰图片使用空替代文本，承载角色含义的图片需有可读替代文本。

## 7. 权限与安全规则

- 用户只能创建、更新、删除和重新同步自己的卡片。
- 备份导入来源必须同时校验 `backup_id/user_id` 和 profile 是否真实存在。
- 私密或草稿卡片不得出现在公开展示墙、公开检索或帖子预览 DTO 中。
- 富文本沿用现有安全渲染路径，并阻止脚本、事件属性和不允许的 URL 协议。
- 图片上传遵守现有图片校验和存储机制，不接受任意远程 URL 绕过。
- 删除卡片后，帖子中的历史链接只显示不可用占位，不级联删除帖子内容。

## 9. 本期不做

- 自动、后台或无提示地覆盖 TRP3 本地文件。
- 将背景故事、第一印象、其他富文本转换并写入 TRP3。
- 移动端完整编辑器适配。
- 人物卡协作编辑、点赞收藏或全站人物卡搜索。
- 因删除人物卡而改写已有帖子正文。

## 10. 安全发布与 TRP3 写回迭代

### 10.1 公开审核

- 人物卡保存为公开状态后进入 `pending`，由版主中心统一审核；版主可通过或驳回并留下理由。
- 对外列表、详情、帖子预览和图片接口只读取 `approved` 快照。
- 所有者读取工作副本，并能区分待审、通过和驳回状态。

### 10.2 RPBox 转 TRP3

- RPBox 人物卡可生成兼容 TRP3 的 profile JSON/Lua；转换范围仅限第 2.2 节的共用基础字段。
- 从备份导入的卡可以写回原 profile；从零创建的卡可以选择账号并建立新的 profile ID。
- 写回属于危险操作：必须使用 `RDialog` 明示目标账号、profile 与覆盖范围，并要求用户确认魔兽世界已关闭。

### 10.3 多版本保护

- 每次修改 TRP3 数据前必须先保存当前版本，不能由调用端跳过；回退前同样先保存当前版本，确保可以撤销回退。
- 版本默认名称为“保存时间 + 内容哈希”，用户可以重命名。
- 用户可以查看版本元数据和内容、自由回退、删除指定档案；所有接口必须同时校验用户、账号和版本归属。
- 云端账号备份历史与桌面端本地文件快照都遵循这一规则，不能只保留一个会被下次写入覆盖的 `.rpbox_backup` 文件。
